## 명사 대신 동사를 쓴다

동사에서 나온 명사(「설정 수행」, 「검토 진행」)는 뜻을 흐린다. 「수행하다」, 「실행하다」, 「진행하다」는 빼도 뜻이 전해진다. 영어는 동사를 명사형(-tion, -ing, -ment)으로 바꿔 쓰는 게 자연스럽지만 한국어는 동사 그대로가 자연스럽다.

- 「코드 최적화 진행 후 배포 수행이 필요합니다.」 → 「코드를 최적화한 후 배포하세요」
- 「MongoDB 연결 정보 설정 및 초기화가 필요합니다.」 → 「MongoDB에 연결할 호스트와 포트를 설정하고 데이터베이스를 초기화합니다.」
- 「로그 파일을 삭제하는 작업을 수행합니다.」 → 「로그 파일을 삭제합니다.」
- 「API 키를 이용한 사용자 인증 처리가 완료된 후, 데이터베이스 접속 설정 진행이 가능합니다.」 → 「API 키로 사용자를 인증한 후, 데이터베이스에 접속하도록 설정할 수 있습니다.」
- 「시스템 모니터링 수행을 통해 서버 성능 측정 작업을 실시하게 됩니다.」 → 「시스템을 모니터링해서 서버 성능을 측정합니다.」
- 「보안 정책 업데이트 진행 후 시스템 재시작 처리를 수행해야 합니다.」 → 「보안 정책을 업데이트한 후 시스템을 재시작합니다.」
- 「설정 변경을 수행한 후 적용을 진행합니다.」 → 「설정을 바꾼 뒤 적용합니다.」
- 「이 API를 통해 데이터를 가져올 수 있습니다.」 → 「이 API로 데이터를 가져올 수 있습니다.」

## 모호한 표현 대신 확실한 정보를 쓴다

「가능성이 있다」, 「일부 경우」, 「필요할 수도 있다」를 쓰면 읽는 사람이 정확한 뜻을 알 수 없다.

- 「설정 파일을 변경하면 기존 설정이 영향을 받을 수도 있습니다.」 → 「설정 파일을 변경하면 기존 설정이 삭제됩니다.」
- 「일부 브라우저에서 정상적으로 동작하지 않을 가능성이 있습니다.」 → 「Internet Explorer에서는 정상적으로 동작하지 않습니다.」

우리 기준: 확인한 것만 단정한다. 확인하지 못했으면 얼버무리지도 단정하지도 말고 「미확인」과 이유를 쓴다.

## 누가, 무엇을, 어디에, 어떻게 하는지 쓴다

생략하면 읽는 사람이 맥락에 기대야 뜻을 안다.

- 「파일을 업로드하면 자동으로 저장됩니다.」 → 「사용자가 파일을 업로드하면 서버에 자동으로 저장됩니다.」
- 「설정을 변경하면 적용됩니다.」 → 「관리자가 설정을 변경하면 변경 사항이 프로덕션 환경에 즉시 적용됩니다.」
- 「에러가 발생하면 로그를 확인하세요.」 → 「에러가 발생하면 애플리케이션 서버에서 에러 로그 파일(`/var/log/app/error.log`)을 확인하세요.」

우리 기준: 문서와 지시문에 적용한다. 대화 답에서 문맥으로 이미 아는 주어는 뺀다(korean-style.md 「조사와 어미를 빼지 않는다」).

## 실제 동작을 쓴다

업계에서만 통하는 표현은 실제 동작을 흐린다.

- 「에러가 발생하면 Exception을 던집니다.」 → 「에러가 발생하면 예외(`Exception`)를 일으킵니다.」 「던지다」는 `throw Exception`을 그대로 옮긴 말이라 호출한 쪽에 넘긴다는 뜻인지 오류를 돌려준다는 뜻인지 사람마다 다르게 읽는다.
- 「클라이언트가 서버를 찔러서 응답을 확인합니다.」 → 「클라이언트가 서버에 요청을 보내서 응답을 확인합니다.」

## 수치와 기준을 쓴다

「많을 때」, 「빠르게」, 「값」, 「성능」은 문맥에 따라 다르게 읽힌다.

- 「데이터가 많을 때는 성능이 저하될 수 있습니다.」 → 「데이터가 10,000건을 넘으면 응답 시간이 1초 이상 걸립니다.」

우리 기준: 수치는 측정이나 자료에 근거가 있을 때만 쓴다. 근거가 없으면 수치를 지어내지 않는다.

## 참조하는 내용의 맥락을 밝힌다

앞에서 나온 변수나 설정을 다시 쓸 때는 어디서 설명했는지, 처음 꺼낼 때는 어디에 쓰는지 알려 준다.

- 「1. API 키를 생성합니다. `apiKey` 변수에 저장합니다. … 3. `apiKey`로 API 인증을 수행합니다.」 → 「1. API 키를 생성하고 `apiKey` 변수에 저장합니다. 이 키는 3단계에서 API 키 인증에 사용됩니다. … 3. 1단계에서 `apiKey`에 저장한 API 키로 인증합니다.」

## 문장은 짧게, 메타 담화는 줄인다

한 문장에는 생각 하나만 담는다. 메타 담화는 「말에 대한 말」이다. 글의 흐름을 설명하는 말(「다음으로」, 「앞서 설명했듯이」, 「이제 알아보겠습니다」), 불필요한 강조(「사실은」, 「솔직히 말하면」, 「결론적으로」), 독자의 반응을 유도하는 말(「아시겠지만」, 「여러분도 아실 것입니다」)이 여기에 든다.

- 「버튼을 클릭하면 다음 단계로 이동하게 되며, 그 이후의 작업을 진행할 수 있습니다.」 → 「버튼을 클릭하면 다음 단계로 이동합니다. 이동 후 이어서 작업을 진행하세요.」
- 「이 API를 호출할 때 요청 헤더를 포함해야 하며, 올바른 인증 정보를 제공해야 정상적으로 응답을 받을 수 있습니다.」 → 「이 API를 호출할 때 요청 헤더와 인증 정보를 포함하세요.」
- 「앞에서 설명했지만, 결론은 이 설정을 변경하는 것이 가장 효과적인 방법이라는 겁니다.」 → 「이 설정을 변경하는 것이 가장 효과적인 방법입니다.」
- 「아시다시피, 이 설정은 성능에 영향을 줍니다.」 → 「이 설정은 성능에 영향을 줍니다.」

## 읽는 사람을 행동의 주체로, 능동형으로 쓴다

문서에 적힌 일을 하는 사람은 읽는 사람이다. 도구나 기술을 주어로 쓰면 어색할 때가 많다. 다만 도구나 기술의 동작 자체를 설명할 때는 도구가 주어가 될 수 있다.

- 「이 라이브러리는 데이터베이스 초기화를 수행해요.」 → 「이 명령어를 실행하면 데이터베이스를 초기화할 수 있어요.」
- 「애플리케이션이 실행되기 전에 설정이 완료되어야 합니다.」 → 「애플리케이션을 실행하기 전에 설정을 완료하세요.」
- 「변경 사항이 적용된 후 다시 빌드되어야 합니다.」 → 「변경 사항을 적용한 후 다시 빌드하세요.」
- 「이 문서는 업데이트된 이후 다시 검토될 필요가 있습니다.」 → 「이 문서를 업데이트한 후 다시 검토하세요.」

우리 기준: 원문 예문 일부는 해요체다. 우리 답은 합니다체로 쓴다.

## 용어를 일관되게 쓴다

- 기술 용어는 공식 표기를 따른다. 「K8을 사용하면 애플리케이션 배포가 쉬워집니다.」 → 「쿠버네티스(Kubernetes)를 사용하면 애플리케이션 배포가 쉬워집니다.」
- 같은 개념을 여러 말로 부르지 않는다. 한 글에서 「추가」, 「첨부」, 「넣다」를 섞어 쓰면 읽는 사람이 헷갈린다. 하나(예: 「업로드」)로 통일한다.
- 약어는 처음 나올 때 풀어 쓴다. 「이 기능은 SSR을 지원합니다.」 → 「이 기능은 SSR(Server-Side Rendering)을 지원합니다.」 약어와 괄호 사이는 띄우지 않는다.

## 가치를 먼저 쓴다

읽는 사람은 「이게 왜 필요한가」, 「내게 무슨 도움이 되나」를 먼저 알고 싶어 한다. 배경이나 기능 목록보다 얻을 수 있는 것을 먼저 쓴다. 두괄식 규칙(writing.md)과 같은 방향이다.

- 「리버스 프록시 설정은 2019년에 도입되었고, 많은 수정이 있었습니다...」 → 「리버스 프록시 설정을 적용하면 네트워크 지연 문제를 최소화할 수 있어요.」
- 「이 스니펫은 다양한 설정 옵션을 제공합니다. 먼저 `connection_timeout`, `retry_attempts`, `max_pool_size` 등의 매개변수를 수정하세요.」 → 「이 스니펫을 사용하면 PostgreSQL 데이터베이스 연결 속도가 50% 빨라집니다.」
