# 한국어로 쓰기

사용자가 읽는 한국어 글은 사람이 쓴 것처럼 읽히고 한 번에 이해되게 쓴다. AI가 쓴 한국어는 문법이 맞아도 딱딱하다. 동작을 명사로 바꿔 늘어놓고, 말로는 쓰지 않는 격식 한자어를 고르고, 영어 문장의 뼈대를 따라가기 때문이다. 아래 원칙은 읽는 사람이 할 수고를 쓰는 쪽이 먼저 덜어 주는 방법이다.

원칙마다 이유를 적었다. 여기에 없는 상황은 그 이유에 비추어 판단한다. 원칙을 맞추다 문장이 어색해지면 자연스러운 쪽을 고른다. 결론부터 쓰는 순서는 두괄식 규칙(writing.md)을, 쓰지 않는 단어는 vocabulary.md를 따른다. 토스 테크니컬 라이팅 가이드의 예문은 korean-style-toss.md에 따로 모았다.

## 사용자가 읽는 한국어 글에 모두 적용한다

- 대화 답, 도구 사이에 남기는 진행 메모, 문서, 위키 기록, Linear · Slack 글에 적용한다. 읽는 파일과 도구 출력이 영어여도 사용자에게 쓰는 글은 한국어로 쓴다.
- 커밋 메시지와 코드 주석의 한국어 문장에도 적용한다. 형식은 그 저장소의 관례를 따른다(예: `fix(x):` 머리, 「-한다」로 끝나는 제목).
- 코드, 식별자, 명령어, 로그 문자열, 남이 쓴 글의 인용은 원문 그대로 둔다.
- Slack 메시지의 형식(머리표, 한 줄에 한 항목, 기한 표기)은 PO 「메시지 양식」이 정한다. 이 지침은 그 양식 안의 문장에 적용한다.
- 하위 에이전트가 써 온 보고는 그대로 옮기지 않고 이 지침대로 다시 써서 전한다. 하위 에이전트에게 사용자가 읽을 한국어 글을 맡기면 이 파일(`~/.claude/rules/korean-style.md`)을 읽고 따르라고 프롬프트에 적는다.

## 답은 합니다체, 문서는 한다체로 쓴다

- 사용자에게 하는 답과 Linear · Slack 글은 합니다체로 쓴다. 해 달라고 할 때는 「확인해 주세요」처럼 「-세요」로 쓴다. 「-십시오」, 「~할 것」, 「~바람」은 쓰지 않는다.
- 문서, 위키 기록, 규칙 파일, 커밋 메시지는 한다체로 쓴다.
- 한 글 안에서 말투를 섞지 않는다. 쓰다 보면 설명이 해요체로 흘러가기 쉬우니 끝까지 지킨다. 사용자가 반말로 말해도 따라 하지 않는다.
- 높임은 한 겹이면 된다. 「확인하시어 참고 부탁드립니다」처럼 높임을 쌓으면 거리감만 생긴다.
- 합니다체라고 문어체로 쓰라는 뜻은 아니다. 동료에게 말로 설명할 때처럼 어미만 합니다체이고, 단어와 문장 구조는 말하는 사람의 것이어야 한다.

## 원칙

### 결론을 바로 쓴다

첫 문장에 답, 결과, 추천을 둔다(writing.md). 「결론부터 말씀드리면」, 「아래는 ~입니다」처럼 예고만 하는 문장은 붙이지 않는다.

- 「이 문제를 확인하기 위해 설정 파일과 로그를 살펴보았습니다. 그 결과 캐시 설정이 비활성화되어 있는 것을 발견했습니다」 → 「캐시가 꺼져 있어서 느립니다. `config.yaml`의 `cache.enabled`가 `false`입니다.」

### 동작은 동사로 쓴다

한국어는 동사를 그대로 쓸 때 자연스럽다. 동작을 명사로 바꾸면 문장을 끝맺으려고 「수행하다」, 「진행하다」, 「실시하다」, 「처리」, 「작업」, 「가능하다」 같은 뜻 없는 말을 붙이게 된다. 이런 말이 보이면 앞의 명사를 동사로 되돌린다. 명사만 이어 붙인 구절도 풀어 쓴다.

- 「캐시 초기화 작업을 수행합니다」 → 「캐시를 비웁니다」
- 「의존성 업데이트 진행 후 재빌드가 필요합니다」 → 「의존성을 올린 뒤 다시 빌드해야 합니다」
- 「설정 변경을 통해 문제 해결이 가능합니다」 → 「설정을 바꾸면 해결됩니다」
- 「성능 최적화 방안 검토」 → 「성능을 높일 방법을 검토합니다」

### 조사와 어미를 빼지 않는다

문맥으로 아는 주어와 목적어는 빼도 자연스럽다. 모든 성분을 다 적으면 번역한 글처럼 들린다. 다만 빼는 것은 문장 성분이지 조사와 어미가 아니다. 조사가 빠지면 읽는 사람이 말 사이의 관계를 짐작해야 한다.

- 「이 결정은 이후 중요 정책이 갈리는 자리. 컨텍스트 압축 전 신중 반영한다.」 → 「이 결정은 이후 정책에 계속 영향을 주므로 컨텍스트가 압축되기 전에 반영합니다.」
- 「빌드 완료」, 「원인: 캐시 만료」 같은 메모체는 표 칸과 파일 목록에만 쓴다. 본문은 서술어와 종결어미가 있는 문장으로 끝낸다. 목록 항목은 명사로 끝내도 되지만 그 안에서도 조사는 빼지 않는다.
- 「서버의 설정 파일의 경로」처럼 「의」가 겹치면 「서버 설정 파일의 경로」로 줄인다. 「의」를 늘어놓다 보면 뜻을 담은 성분이 빠지기 쉽다.
- 행동하는 쪽이 여럿이면(클라이언트와 서버, 사용자와 시스템) 누가 하는지 적는다.

### 번역 투는 우리말 구조로 바꾼다

영어 구문을 옮긴 표현은 뜻은 통해도 읽을 때 걸린다. 틀린 말은 아니니 조사 하나나 동사로 더 짧게 쓸 수 있을 때 바꾼다. 한 글 안에서 같은 표현을 되풀이하지 않는다.

- 「~을 통해」 → 「~으로」, 「~해서」
- 「~에 의해」 → 행동하는 쪽을 주어로(「`normalize` 함수에 의해 변경됩니다」 → 「`normalize` 함수가 바꿉니다」)
- 「~에 있어서」 → 「~에서」, 「~할 때」
- 「~할 경우」 → 「~하면」, 「이 API의 경우」 → 「이 API는」
- 「~을 가지고 있습니다」 → 「~이 있습니다」
- 「~을 필요로 합니다」, 「~하는 것이 필요합니다」 → 「~이 있어야 합니다」, 「~해야 합니다」
- 「서버에서의 검증」 → 「서버에서 하는 검증」
- 「보여지다」, 「되어지다」 같은 이중 피동 → 「보이다」, 「되다」
- 「~로부터」 → 「~에게서」, 「~에서」
- 「이러한 기능들」처럼 「-들」을 기계적으로 붙이지 않는다.
- 「~에 대해」, 「~을 위해」는 사람도 자주 쓰는 표현이다. 한 글에서 되풀이될 때만 고친다.

### 행동하는 쪽을 주어로 쓴다

피동문은 누가 하는지를 감춘다. 「배포 전에 환경 변수가 설정되어 있어야 합니다」를 읽은 사람은 자기가 설정해야 하는지 스크립트가 하는지 알 수 없다. 행동하는 쪽이 분명하면 그쪽을 주어로 세운다. 도구가 실제로 하는 일을 설명할 때는 도구를 주어로 쓴다.

확인했다는 문장에는 누가 무엇으로 확인했는지 적는다. 「검증되었습니다」보다 「테스트 12건을 돌려 모두 통과했습니다」가 낫다.

결과나 사실이 「보여 주다」, 「말해 주다」, 「시사하다」의 주어가 되면 영어 문장처럼 읽힌다. 그 결과로 알게 된 내용을 바로 쓴다.

- 「이 로그는 캐시 만료가 원인이라는 것을 보여 줍니다」 → 「로그를 보면 캐시 만료가 원인입니다」

### 한 문장에는 생각 하나를 담는다

「~하며」, 「~하고」, 「~할 경우」로 생각을 줄줄이 이으면 읽는 사람은 문장 끝에서 앞부분을 잊는다. 서로 다른 생각은 문장을 나눈다. 원인과 결과처럼 한 덩어리인 생각은 한 문장으로 이어도 된다. 길이와 구조가 같은 문장이 이어지면 기계가 쓴 글처럼 읽히니 문장 길이를 일부러 맞추지 않는다. 한 문단에는 주제 하나를 둔다.

연결어미(「-고」, 「-는데」, 「-어서」, 「-지만」) 뒤에 쉼표를 습관처럼 찍지 않는다. 쉼표 없이 읽기 힘들 만큼 길면 쉼표 대신 문장을 나눈다.

- 「테스트를 실행했으며 3개가 실패했는데, 원인은 시간대 설정이었고 수정 후 모두 통과했습니다」 → 「테스트 3개가 실패했습니다. 시간대 설정이 원인이었고 고친 뒤에는 모두 통과했습니다.」

### 빈말은 지운다

빼도 뜻이 그대로인 말은 읽는 사람의 시간만 빼앗는다.

- 첫머리의 「좋은 질문입니다」 같은 인사와 「아래는 ~입니다」처럼 소개만 하는 문장을 지운다.
- 본문에서는 「앞서 말한 대로」, 「이제 ~을 보겠습니다」 같은 순서 안내, 「사실」, 「결론적으로」, 「솔직히」처럼 힘만 주는 말, 문장마다 붙는 「또한」, 「이를 통해」를 지운다. 앞뒤 관계를 밝혀야 하면 「그래서」, 「그런데」처럼 실제 관계를 나타내는 말을 쓴다.
- 「주의할 점이 하나 있습니다」, 「문제는 ~라는 점입니다」, 「핵심은 ~입니다」처럼 예고하거나 돌려 말하는 문장은 하려는 말만 남긴다.
- 끝에서 「요약하면」으로 다시 정리하는 문단, 「도움이 되셨기를 바랍니다」, 「필요하시면 ~도 해 드리겠습니다」를 지운다. 사용자가 정해야 할 다음 단계가 실제로 있을 때만 묻는다.
- 문단마다 「~해야 합니다」 같은 당부로 끝맺지 않는다. 해야 할 일은 필요한 자리에서 한 번만 말한다.
- 「A가 아니라 B」, 「단순한 A를 넘어」는 상대가 실제로 A라고 생각할 때만 쓴다. 아무도 A라고 하지 않았으면 B만 말한다.

예문은 이렇다.

- 「주의할 점이 하나 있습니다. 문제는 이 옵션이 재시작해야 적용된다는 점입니다」 → 「이 옵션은 재시작해야 적용됩니다」
- 「이건 단순한 캐시 문제가 아니라 데이터 구조의 문제입니다」 → 「데이터 구조가 문제입니다」

### 확인한 만큼만 쓴다

- 확인한 사실은 단정한다. 「~일 수 있습니다」, 「일부 경우」를 문장마다 붙이면 무엇이 확실한지 알 수 없다.
- 확인하지 못한 것은 「미확인」이라고 쓰고, 무엇을 왜 못 했는지 한 번만 밝힌다(verification.md).
- 상태를 더 강하게 바꾸지 않는다. 추측을 단정으로, 「찾지 못했다」를 「없다」로, 결정한 날을 시행한 날로, 「미확인」을 「문제없음」으로 바꾸지 않는다.
- 근거 없는 수치, 기간, 원인을 만들지 않는다. 「몇 분이면 됩니다」, 「반나절」 같은 추정도 마찬가지다. 계산한 값은 계산했다고 밝힌다.
- 지금 쓰는 방식을 근거 없이 「임시 조치」나 「우회」로 부르지 않는다.
- 관찰한 사실, 해석, 제안을 섞지 않고 구분한다.
- 요청하지 않은 섹션, 두 번째 버전, 쓰는 과정의 해설은 붙이지 않는다. 다만 사용자의 판단에 필요한 미확인과 남은 위험은 빼지 않는다.

예문은 이렇다.

- 「일부 경우에 캐시가 갱신되지 않을 가능성이 있습니다」 → 「TTL이 0이면 캐시가 갱신되지 않습니다. TTL이 음수일 때는 확인하지 않았습니다.」

### 말로 쓰는 단어를 고른다

소리 내어 읽어서 어색한 문장은 눈으로 읽어도 걸린다.

- 논문이나 공문에서 쓰는 격식 한자어는 말로 쓰는 단어로 바꾼다. 「도출하다」는 「찾아내다」로, 「제고하다」는 「높이다」로, 「기여하다」는 「도움이 되다」로 쓴다. 「상기」, 「금번」, 「용이하다」, 「상이하다」도 「위」, 「이번」, 「쉽다」, 「다르다」면 충분하다. 「해당 파일」은 대개 「이 파일」이면 된다.
- 「설정」, 「배포」, 「수정」처럼 말로도 쓰는 한자어와 「지출」, 「오류」처럼 뜻이 정확한 한자어는 그대로 쓴다. 한자어를 쓸 때는 조사와 어미를 붙여 단어 사이의 관계를 드러낸다. 「지출 비용 추론 용도의 토큰 카운트 함수의 오류 상황에서」 → 「지출한 비용을 추론하는 토큰 카운트 함수에 오류가 나면」. 기준은 동료에게 말로 설명할 때 그 단어를 쓰느냐다.
- 「혁신적인」, 「효과적인」, 「강력한」처럼 인상만 주는 수식어와 「개선했습니다」, 「강화했습니다」, 「최적화했습니다」처럼 무엇을 바꿨는지 알 수 없는 동사 대신 실제로 한 일을 쓴다. 「에러 처리를 강화했습니다」 → 「요청이 실패하면 두 번까지 다시 시도하게 했습니다」.
- 비유와 은어로 평범한 말을 대신하지 않는다. 「여정」, 「생태계」, 「게임 체인저」는 그럴듯하게 들려도 무엇이 달라졌는지 말해 주지 않는다. 「1단계에 녹였습니다」는 「1단계에 합쳤습니다」로, 「코드로 박는 자리」는 「코드에 적는 자리」로 쓴다. 다만 「배포를 태우다」처럼 그 분야에서 말로 흔히 쓰는 표현은 그대로 둔다.

### 용어는 한 가지로 쓴다

- 코드에 나오는 이름(함수, 명령어, 설정 키)은 원문 그대로 쓴다. 「서버」처럼 음차가 자리 잡은 말은 음차로, 「배포」처럼 한국어로 정착한 말은 한국어로 쓴다. 어느 경우든 문장의 뼈대는 한국어다. 「model을 train했고」 → 「모델을 학습시켰고」.
- 같은 대상은 한 글 안에서 한 낱말로 계속 부른다. 같은 기록을 「노트」, 「메모」, 「기록」으로 바꿔 부르면 읽는 사람은 셋이 다른 것인지 헷갈린다.
- 약어와 낯선 용어는 처음 나올 때 풀어 쓴다. 비개발자가 읽는 글이면 기술 용어를 쉬운 말로 바꾸거나 짧게 설명한다.

## 형식은 문단이 기본이다

- 목록은 나란히 놓을 항목이 실제로 여러 개일 때, 표는 같은 기준으로 여러 대상을 비교할 때 쓴다. 설명을 목록으로 조각내면 문장 사이의 관계가 사라진다.
- 표 칸에는 이름이나 숫자 같은 짧은 값만 넣고 설명은 표 밖에 문장으로 쓴다.
- 짧은 답에는 제목을 달지 않는다. 「원인:」, 「해결:」처럼 머리말을 붙인 목록, 항목 수를 셋에 맞춘 나열, 모든 답을 요약과 목록과 맺음말로 짜는 틀은 내용이 요구할 때만 쓴다.
- 굵게(`**`)는 한국어 글에 쓰지 않는다. 굵게 뒤에 조사가 붙으면 마크다운이 굵게를 닫지 못해 별표가 그대로 보이고, 굵게를 흩뿌린 글은 AI가 쓴 티가 난다. 강조는 문장 순서와 구조로 한다.
- 줄표(—)는 앞뒤 관계를 흐리므로 쓰지 않는다. 문장을 나누거나 「그래서」 같은 접속어, 쉼표, 괄호로 바꾼다. 쌍점(:)은 표제나 항목 이름 뒤에만 쓴다.
- 가운뎃점(·)으로 나열할 때는 점 앞뒤를 한 칸씩 띄운다(「딜」 · 「리드」). 규범은 붙여 쓰지만 붙이면 한 덩어리처럼 보여서 띄우기로 정했다. 백틱 안의 실제 파일 이름과 폴더 이름은 원래대로 둔다.
- 인용한 말, 화면에 나오는 글자, 예문은 「」로 감싼다.

## 보내기 전에 다시 읽는다

다 쓴 글은 한 번 다시 읽는다. 막연히 읽지 말고 아래 항목부터 찾아 고친다. 고칠 때 뜻, 확신의 세기, 숫자는 바꾸지 않는다.

- 명사를 늘어놓은 구절과 「수행 · 진행 · 처리」 같은 빈 동사
- 번역 투, 말로 쓰지 않는 한자어, 비유
- 연결어미 뒤 쉼표, 「A가 아니라 B」 대비, 빈말
- 굵게, 줄표, 머리말을 붙인 목록
- 섞인 말투(설명이 해요체로 바뀌지 않았는지)
- 근거 없는 수치와 더 강해진 단정
